# Scope baseline and work breakdown structure

## Scope statement

Release 1 will design, produce, quality-check, and publish a coherent 30-part beginner IT series spoken primarily in Haitian Creole, one post per day for 30 consecutive days. It will establish a repeatable production system, preserve project evidence in GitHub, and conduct audience evaluation only after the final post.

The charter controls high-level scope. This document decomposes the accepted deliverables into manageable work packages.

## Product scope

The learner receives:

- 30 numbered, connected, short-form lessons;
- plain-language Haitian Creole explanations;
- English technical vocabulary where it helps transfer to interfaces and jobs;
- practical examples and a small recall/application prompt;
- accessible captions and safe demonstrations;
- a public curriculum/reference trail in GitHub.

## Project scope

The team performs:

- initiation, planning, governance, and reporting;
- audience and terminology discovery;
- curriculum architecture and episode research;
- scripting, recording, editing, captioning, and QA;
- publication and comment moderation;
- posted/not-posted control only during the challenge;
- measurement, analysis, retrospective, and decision after Day 30;
- repository maintenance and portfolio presentation.

## Deliverable-oriented WBS

```text
1.0 Project governance
  1.1 Charter and baselines
  1.2 Status, change, decision, and issue control
  1.3 Stage-gate reviews
2.0 Audience and value discovery
  2.1 Audience hypothesis
  2.2 Five lightweight learner conversations
  2.3 TikTok search/content-gap review
  2.4 Learner problem and vocabulary findings
3.0 Curriculum package
  3.1 Learning architecture
  3.2 Thirty episode briefs
  3.3 Source and terminology records
  3.4 Sequence and dependency review
4.0 Production system
  4.1 Brand and visual conventions
  4.2 Recording/editing workflow
  4.3 File naming and storage
  4.4 Templates and Kanban policies
  4.5 Backup publishing procedure
5.0 Content increments (01–30)
  5.x.1 Script
  5.x.2 Record
  5.x.3 Edit and captions
  5.x.4 Creator technical/language/safety QA
  5.x.5 Schedule and publish
6.0 Community and protection
  6.1 Comment moderation rules
  6.2 Corrections and incident process
  6.3 Privacy/copyright control
7.0 Measurement and learning
  7.1 Analytics blackout control
  7.2 Day-31 baseline snapshot
  7.3 Qualitative coding
  7.4 Day-38 follow-up snapshot
  7.5 Evaluation and retrospective
8.0 Portfolio repository
  8.1 Navigation and documentation
  8.2 Issues, labels, and milestone
  8.3 Validation and release notes
```

`5.x` means the same content work package is repeated for episode IDs `E01` through `E30`.

## WBS dictionary

| WBS | Work package | Owner | Completion evidence |
|---|---|---|---|
| 1.1 | Management baseline | Project manager | Sponsor-reviewed charter, scope, schedule, budget, quality, communication, and risk documents |
| 2.2 | Learner conversations | Creator | De-identified notes from five target learners; consent respected |
| 2.3 | Search review | Creator | Dated list of relevant searches/content gaps; no private account data committed |
| 3.2 | Episode briefs | Content owner | 30 briefs meet Definition of Ready |
| 3.3 | Sources/terms | Creator review owner | Every material claim sourced; disputed terms flagged and resolved or explained |
| 4.2 | Workflow | Creator | One sample travels from brief to ready-to-post without an undocumented step |
| 4.5 | Backup procedure | Creator | A second device/network/manual-post path is checked where practical |
| 5.x | Episode increment | Creator | Final file passes the creator's Definition of Done; only posted yes/no is recorded during Days 1–30 |
| 6.2 | Corrections | Creator | Immediate protection when needed; project detail recorded only after the blackout unless containment requires otherwise |
| 7.2 | Baseline snapshot | Analyst/creator | Snapshot collected only after E30 is public, with collection timestamp and exposure age |
| 7.5 | Evaluation | Sponsor and creator | Findings, limits, lessons, and decision are documented |
| 8.0 | Portfolio | Project manager | Public repo is navigable, current, and free of known secrets/private data |

## Scope exclusions and boundary rules

- A comment asking for personal troubleshooting does not automatically enter scope. It becomes an anonymized content idea or is referred to appropriate support.
- A topic that requires dangerous commands, real malware, credential handling, or access to another person's account is excluded from demonstrations.
- Advanced requests go into a future backlog; they do not displace the foundational 30 without sponsor-approved change.
- Performance-driven topic changes wait until after Gate 2.
- Corrections for safety and accuracy are not scope creep; they are quality work.

## Acceptance and validation

The sponsor accepts the release at Gate 2 using the 30 posted/not-posted flags. Pre-launch quality evidence remains available, but challenge-period quality and exception evidence is deliberately absent under the sponsor's strict blackout. Audience value is evaluated separately at Gate 3, with that evidence limitation stated explicitly.

## PM lesson: why a WBS is deliverable-oriented

A work breakdown structure answers, “What complete pieces must exist?” It is not just a chronological to-do list. Breaking the release into reviewable deliverables helps estimate work, assign ownership, identify missing scope, and trace acceptance.
